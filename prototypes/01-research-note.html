Research note · 19 Sep 2026 · for Dwight

Sandlot Derby

Is there a “Desert Golfing, but baseball”? Could we ship one on the App Store in native Swift? Short answer: nobody has made the bare version, the physics is small, and SpriteKit is the right tool. One premise needs correcting first.

Does it exist?
Not really
Flick-to-hit games exist (Flick Home Run!, Baseball Boy!), all wrapped in upgrades, ads, and modes. No endless, menu-free, one-gesture baseball game was found.
Could we build it?
Yes
One projectile, gravity plus quadratic drag, one gesture, a wall. Smaller than g0lf: no terrain collision.
Must it be Swift?
Should be
“Apple shuns JS apps” is mostly a myth. But for a physics game with no web reuse, SpriteKit is simpler and smoother than a WebView.

2. Try the two candidate mechanics

The design question is which single gesture to build around. Flick Home Run! uses a timed swipe. Your g0lf uses a drag vector. This toy runs both against the same flight model so you can feel the difference. Drag is real baseball drag, calibrated so 100 mph at 28° lands near 400 ft.

What the toy suggests

  • Timing is more “baseball” but it is a rhythm input, not a physics input. The player controls one scalar (when). Angle and power are derived from it, so the design has to invent that mapping.
  • Flick is more Desert Golfing. The player owns the launch vector directly, the same feel as g0lf. The pitch becomes flavour, not input. It also makes the outcome legible: you see exactly why the ball did what it did.
  • A hybrid is tempting (flick sets angle and power, pitch timing scales contact quality) but it doubles the input model. Desert Golfing’s whole point was that it never did that.

3. The physics, and why it is smaller than g0lf

A batted ball is one body with two forces. Gravity is constant. Air drag grows with the square of speed, and at 100 mph it is about 1.2 times the ball’s weight, which is why a batted ball goes 400 ft and not 560. Backspin adds a lift term that is worth about 50 ft on a well-hit ball. Everything else is presentation.

Statcast’s rule of thumb is that 100 mph at about 28° is a 400 ft ball, and that the best launch angles are 25–35°. Both fall out of this model, which is the sanity check that the constants are right. Real backspin lift is stronger than the fixed 0.15 used here, so the model slightly under-rewards high, spinny hits.

Integrator

Semi-implicit Euler at a fixed step is enough. The toy runs 4 substeps per frame at 60 Hz. There is no terrain: the only collisions are a flat ground line and one vertical wall, so the hard part of g0lf (segment collision against a procedural polyline) does not exist here.

// per substep, dt = 1/240 s, SI units
let speed = hypot(vx, vy)
let ax = -k * cd * speed * vx - k * lift * speed * vy
let ay = -g - k * cd * speed * vy + k * lift * speed * vx
vx += ax * dt;  vy += ay * dt
x  += vx * dt;  y  += vy * dt
if y < 0 { y = 0; vy = -vy * 0.4; vx *= 0.75 }   // bounce, then roll

4. Fact-check: does Apple shun JS apps?

Mostly a myth. Nothing in the current App Store Review Guidelines bans JavaScript, Capacitor, Cordova, React Native, or a Phaser game inside a WKWebView. The rule people remember is about something else.

  • 2.5.2 says apps may not “download, install, or execute code which introduces or changes features or functionality.” That targets loading new logic from a server after review, not the language the bundle was compiled from.
  • 2.5.6 says apps that browse the web must use WebKit. That is about browsers, not games.
  • 4.2 Minimum Functionality is the one that actually rejects things: an app that is “not particularly useful, unique, or ‘app-like’” or is “a repackaged website.” It is a judgement about feel, and a laggy WebView with no haptics, no offline, and browser-style scrolling fails it.
  • 4.7 explicitly permits “HTML5 and JavaScript mini apps and mini games” inside a host app, which is the clearest proof there is no class ban. BBC Games ships its kids’ games through Ionic Capacitor, and Phaser publishes an official Capacitor-to-App-Store guide.

So the honest version of the premise is: a web-tech game is allowed, but it has to feel native, and a WebView makes that harder. For a physics toy where 60 fps touch response is the entire product, that is a real cost. The reason to go Swift is not compliance. It is that SpriteKit gives you the frame loop, the physics, Game Center, and haptics for free, and there is no web version of this game to share code with.

Guideline text read from developer.apple.com/app-store/review/guidelines on 19 Sep 2026. The one thing the researcher could not pin down was a named small indie Phaser game with a live App Store link, so treat “indie HTML5 games ship fine” as strongly implied by 4.7 rather than proven by example.

5. Native stack recommendation

SwiftUI shell, SpriteKit scene, hand-rolled flight. SpriteKit is not deprecated. WWDC 2025 deprecated SceneKit (the 3D one), and forum threads keep conflating the two. SpriteKit still ships with Xcode, renders through Metal, and drops into SwiftUI with SpriteView.

The one real wrinkle: SpriteKit’s built-in linearDamping is proportional to velocity, not velocity squared, so it cannot produce baseball drag. Either apply a per-frame force in the scene’s update, or skip the physics engine for the ball entirely and do what g0lf already does: simulate the whole flight on release and play it back.

Recommended

Precompute and play back

  • On release, integrate the flight once (the loop in section 3) into an array of points.
  • Play it back with SKAction.follow(path) or by stepping the array in update(_:).
  • Deterministic, testable in a plain XCTest with no scene, and identical to the g0lf architecture.
  • No SKPhysicsBody at all. The wall and ground are two if-statements.
Alternative

SKPhysicsBody plus custom force

  • Give the ball a physics body, then each frame call applyForce(−k·|v|·v).
  • Free bounces, wall contact via SKPhysicsContactDelegate.
  • Costs determinism: SpriteKit steps at frame rate, so the same swing can land a foot apart on a busy frame. Bad for a shared seed.

Rejected alternatives

  • Godot 4 or Unity. Real engines for a game with one body and two lines. Both add a second toolchain and an export pipeline to a project that fits in a few Swift files. Unity was also not what Desert Golfing used, despite the folklore.
  • Box2D via Swift bindings. Desert Golfing genuinely ran on Box2D, inside Justin Smith’s own C++ engine, but g0lf already proved the terrain problem does not need an engine, and a derby has no terrain. The researcher could not verify a maintained Swift Box2D package in 2026.
  • SwiftUI Canvas with a TimelineView. Works, and is a fair fallback if SpriteView misbehaves. You lose SKAction and texture atlases but for a silhouette and a ball that is nothing.

6. What carries over from g0lf

More than expected. g0lf does not run physics per frame at all: it integrates the whole shot on release and compiles it to CSS keyframes. That “simulate once, play back” shape is exactly the recommended Swift architecture, so the port is a translation of ideas, not a rewrite of an engine. What changes is that most of the hard code goes away.

Two g0lf lessons apply directly. First, the trajectory cheat deliberately omits wind so the preview stays honest without giving the shot away; a derby ghost line should do the same. Second, g0lf’s unit choice (a 1000×600 virtual space) let the physics ignore screen size. Doing the same here in feet, with one scale factor at draw time, keeps the Flight module testable against real Statcast numbers.

7. Open questions before building

  1. Which gesture. Play the toy in both modes for a few minutes. The one you keep playing is the answer.
  2. What is endless. Desert Golfing’s endlessness is the terrain. In a derby the equivalent is probably the wall: distance and height drift per “park”, seeded, so park 1,000 is a real place you can share.
  3. What is the score. Cumulative feet? Home run count out of pitches? Desert Golfing counts strokes forever and never resets; the honest analogue is total feet, forever.
  4. Name and look. Nothing here depends on a licence. A silhouette batter and a chalk line is enough, and it is the look that makes the minimalism read as intent rather than budget.
